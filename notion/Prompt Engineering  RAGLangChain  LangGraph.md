# Prompt Engineering & RAGLangChain & LangGraph

프롬프트 엔지니어링이란?

프롬프트 엔지니어링(Prompt Engineering)은 대규모 언어 모델(LLM, Large Language Model) 혹은 다양한 자연어 처리(NLP) 모델들을 사용할 때, 추가적인 모델 파인튜닝(재학습) 없이 원하는 출력을 얻기 위해 입력되는 문장의 형식과 내용을 설계하고 최적화하는 과정을 말합니다.

학습없이 성능을 극대화

추가 학습(Training) 없이 즉시 활용

기존의 머신러닝/딥러닝 모델들은 새로운 태스크를 위해 다시 학습하거나 추가 데이터를 준비하여 미세조정이 필요

입력 토큰으로 부터 미래 토큰을 예측하는 GPT 계열 모델 특성 상 입력된 프롬프트에 따라 토큰 생성 흐름이 달라져 결과도 달라짐

즉 모델의 파라미터를 재학습 없이도, 프롬프트 설계만으로 다양한 태스크에 대한 성능을 최적화 가능

프롬프트를 통한 모델 통제

특정 톤·스타일·제한사항을 설정하는 등의 방법을 통해 모델의 답변 스타일을 원하는 방향으로 이끄는 것이 가능

새로운 지식을 제공하거나, 적절한 지시사항, 맥락 정보, 예시 등을 제공함으로써 모델의 성능을 크게 끌어올릴 수 있음

파인튜닝과의 차이

파인튜닝(Fine-tuning)

모델에 추가 데이터를 주고 재학습하여, 특정 도메인(예: 의료, 법률) 혹은 특정 태스크(예: 감성분석, 텍스트 분류)에 맞춰 모델의 파라미터를 업데이트하는 과정

학습에 필요한 리소스와 시간이 매우 크다는 문제가 존재

프롬프트 엔지니어링

모델 자체를 다시 학습하지 않으며, 이미 학습된 거대 모델에 적절한 입력(Prompt)만 설계하여 원하는 응답을 얻는 방식

재학습 비용이 없고, 비교적 빠르게 적용할 수 있다는 장점이 있지만, 모델이 이미 학습한 지식의 범위를 넘어서거나 특정한(매우 세밀한) 도메인 작업에 대해서는 한계가 있을 수 있음

다양한 프롬프트 엔지니어링 기법

프롬프트 엔지니어링 기법은 크게 명령어 작성 방식과 맥락을 주입하는 방식으로 나누어 볼 수 있습니다. 각 방식 내에서도 다양한 변형과 특징이 있습니다.

명령어 스타일에 따른 기법

직접 지시형(Direct Instruction) 프롬프트

“~를 해주세요”, “~를 나열해 주세요”와 같이 원하는 작업을 명확히 지시.

예: “이 텍스트의 핵심 내용을 세 문장으로 요약해 주세요.”

매우 구체적인 상황에 대한 설명과 제약조건을 걸수록 명확한 답변을 얻을 수 있음

역할(Role) 설정 프롬프트

모델에게 특정 역할(예: 전문가, 비서, 평가자)을 부여하여 답변의 스타일이나 관점을 지정.

예: “당신은 유명 셰프입니다. 요리에 대해 매우 전문적인 조언을 해주세요.”

모델이 이해할 수 있도록 충분한 맥락과 역할이 필요

예시 제공(Few-shot Prompting)

모델이 어떤 형태의 출력을 기대하는지 명확히 알 수 있도록 몇 개의 데이터 예시를 제공 

예:

예시를 통해 모델이 출력 형식과 분량, 어조 등을 더욱 명확히 파악 가능

맥락(Context) 주입 방식에 따른 기법

체인 오브 소트(Chain-of-thought) 기법

문제 해결 과정을 모델이 단계별로 생각하도록 유도하는 프롬프트 작성 기법.

예: “다음 문제를 풀 때, 논리적 사고 과정을 천천히 단계별로 설명한 뒤 최종 결론을 도출하세요.”

복잡한 문제에 대한 정확도가 올라가는 경우가 많음

리액트(ReAct, Reason+Act) 기법

모델이 추론(Reason) 단계를 통해 상황을 파악하고, 행동(Act) 단계에서 특정 툴을 호출하여 결과를 얻은 뒤 정답(Answer)을 제시하게 하는 기법

예:

복잡한 응답을 체계적으로 생성 해나가며, 더욱 구체적인 답변이 가능

부연(Elaboration) 및 컨텍스트 확장

모델에게 추가 설명이나 문맥을 충분히 제공하여, 모델이 답변할 때 사용할 ‘배경 지식’을 늘려주는 방식.

예: “시나리오: 당신은 18세기 영국의 문학 평론가이며, 글을 쓸 때마다 고전 문학에 대한 해박한 지식을 드러냅니다. … (구체적 배경 설명) … 이 시에 대한 평론을 작성해 주세요.”

모델이 부가적인 정보를 쉽게 활용하므로, 보다 맞춤형이면서 풍부한 답변을 기대할 수 있음.

RAG(Retrieval-Augmented Generation)

RAG의 개념

기존 LLM의 한계

GPT나 BERT등 LLM 모델은 기본적으로 사전 학습을 통해 자연어에 대한 정보를 파라미터에 저장하기 때문에 아주 방대한 데이터로 사전 학습되었다고 하더라도, 다음과 같은 문제점이 생깁니다.

사전학습 시점 이후에 새로 생성된 지식(최신 정보)을 반영하긴 어려움

모델 파라미터만으로는 한정적인 특정 도메인 세부 정보(규정, 제품 설명 등)를 정확히 반영하기 어려움

또한 모델이 완전하지 않은 정보로 유추하여 환각(잘못된 정보 생성) 문제를 일으킬 수 있음

검색을 활용하는 LLM

정확하고 최신의 정보를 재학습없이 모델에게 전달하기 위해 검색과 맥락 기법을 도입한 RAG가 등장

모델의 내부 파라미터에 의존하지 않고, 외부 지식(문서, FAQ, 데이터베이스 등)을 가져와서 그 내용에 근거해 답변을 생성하는 방식

RAG의 장점

모델이 사전학습을 마친 이후에 새로 나온 정보도, 검색을 통해 실시간으로 반영 가능.

모델이 외부 문서 근거를 토대로 답변하므로, 근거 기반 답변이 늘어나고 환각을 줄일 수 있음

모델 파라미터 자체를 추가로 업데이트하지 않고도, 다양한 도메인 지식을 가져와 특화된 답변을 생성할 수 있음



RAG를 활용한 프롬프트 최적화 절차

질의(Query) 분석

외부 지식 검색

맥락 결합(Contextualization)

언어 모델의 답변 생성

RAG 적용 시 주의사항

적절한 검색 인덱스 구축: 사용하려는 데이터에 대해 정확하고 빠른 검색이 가능한 인덱스 구조가 필요(예: 유사도 검색용 임베딩 인덱스).

문서의 신뢰도 평가: 검색된 문서가 신뢰할 만한 소스인지, 업데이트된 정보인지 등을 반드시 확인

과도한 의존성 주의: 검색된 정보가 항상 정확하거나 충분한 것은 아닐 수 있으므로, 모델이 답변에 활용할 때 교차 검증이 필요

프롬프트 길이 관리: 검색 결과를 과도하게 넣으면, 언어 모델 입력 제한(Token limit)을 넘어설 수 있으니 핵심 요약본만 추려서 제공



에이전트로 확장

프롬프트 엔지니어링과 RAG는 LLM의 답변 품질과 지식 활용 능력을 크게 향상시켰지만, 실시간 정보 조회나 외부 시스템을 통한 실제 작업 수행에는 여전히 한계가 있습니다. 에이전트는 LLM이 검색, 계산, API 호출과 같은 다양한 시스템 도구를 직접 선택하고 실행하게 함으로써, 단순한 답변 생성을 넘어 실제 작업을 수행하는 AI 비서로 확장시키는 핵심 기술입니다.

도구를 활용하기 시작한 LLM

지식과 언어의 한계

프롬프트 엔지니어링과 RAG 기법을 통해 LLM에게 재학습 없이도 지식을 수용하여 언어적인 답변을 유도 할 수 있음

하지만 결과적으로 학습된 데이터나 벡터 DB에 저장된 지식를 기반으로만 답변하는 폐쇠적인 시스템에서는 벗어나지 못함

일반 인공지능을 위해선 언어적인 답변을 넘어 필요한 작업을 직접 판단하고 실행할 수 있는 행동 능력이 요구 

도구의 활용

사람은 신체로 해결하지 못하는 작업이라도, 상황에 적절한 도구를 선택하여 문제를 해결하는 능력을 가짐

LLM 또한 소프트웨어 적인 도구를 활용할 수 있다면 단순 언어적 답변을 넘어서 직접적인 작업 수행 능력을 가질 수 있음

추론 및 계획 (Planning)

복잡한 목표를 하위 작업으로 분해하여 단계별 수행

Chain-of-Thought나 ReAct 기법을 사용하여 현재 맥락에는 어떤 도구를 어떤 순서로 사용해야할 지를 직접 파악

도구 (Tools)

에이전트가 사용할 수 있는 소프트웨어 요소

웹 검색 엔진, 데이터베이스 쿼리 실행기, 문서 요약기, 계산 알고리즘, 정보 수집 API 등이 해당

LLM이 도구를 어떤 상황에 사용해야할지 파악하기 위해 도구에 대한 구체적 설명이 같이 포함되어야 함

메모리 (Memory)

이전 단계에서 얻은 결과나 사용자와의 대화 맥락을 저장

단기 메모리는 현재 작업 흐름을 유지하고, 장기 메모리는 과거의 경험을 학습에 활용

기존 대화가 유기적으로 연결되기 때문에 전체적인 대화 맥락을 고려하여 도구를 사용할 수 있음

제어 로직 (Control Loop)

작업을 완료할 때까지 추론 (도구 판단) -> 행동 (도구 사용) -> 관찰 (도구 결과) 의 과정을 반복

LLM 모델을 한번 사용하고 끝나는 것이 아니라 도구의 결과 값을 맥락에 포함하여 반복적으로 사용

하나의 도구만을 사용하는 것이 아닌 여러개의 도구를 순서대로 사용하여 최종 결과를 만들어 낼 수 있음
